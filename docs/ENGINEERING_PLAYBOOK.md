> المصدر الحاكم للتفاصيل: `AGENTS.md` ووِثائق المشروع المتاحة والقرارات الأحدث (و`docs/PROJECT_CONTEXT.md` إن أُنشئت) ووثائق المجال. عند التعارض حافظ على القرار المعتمد، واصعّد التعارض المؤثر بدل إعادة تصميم النظام صامتًا.

## 1. مبادئ قابلة للتطبيق
1. **الدليل قبل الافتراض:** افحص الشيفرة، مخطط البيانات، الواجهات المستهلكة، التبعيات والتوثيق ذي الصلة؛ فرّق بين منفذ/مخطط/مُختبر/منشور. لا تختلق أمرًا أو ملفًا أو نتيجة.
2. **أقل تغيير صحيح:** فضّل حلول المشروع ومكتباته الموجودة والتوثيق الرسمي، ولا تُدخل إعادة هيكلة أو ميزة غير مطلوبة. لا تجعل "أبسط حل" ذريعة لإهمال العزل أو الأمان أو الموثوقية.
3. **الهدف أولًا:** لكل مهمة عرّف: الغرض، والسلوك الحالي بدليل، والسلوك المقصود، ومعايير القبول، وحدود عدم المساس، والتأثير العكسي.
4. **دفعات صغيرة:** قسّم التغييرات إلى أجزاء يمكن مراجعتها والرجوع عنها؛ افصل إصلاح الخلل عن التنظيف والتحسين الاختياري.
5. **الصراحة المهنية:** ناقش الافتراض الخاطئ بالأدلة؛ اطلب قرارًا فقط إذا تعارض الخيار مع معمارية/صلاحية/تكلفة معتمدة أو كان غير قابل للرجوع.
6. **استعادة المعرفة:** بعد التصحيح، سجّل السبب الجذري والقاعدة الدقيقة التي تمنع تكراره في قسم التعلّم، بدون تحويل الملفات إلى تعليمات طويلة متكررة.

## 2. دورة العمل (Explore → Specify → Implement → Verify → Review → Handoff)
- **Explore:** اقرأ الملفات المتأثرة ومستدعيها، التعليمات الأقرب لمسار التعديل، ثم تحقق من أوامر التشغيل من manifests/CI الموجودة؛ لا تخمّن أوامر اختبار.
- **Specify:** اكتب مثال قبول واقعي قابل للاختبار؛ وفي الخطأ حاول إعادة إنتاج فشل مثبت قبل إصلاحه. لخوارزمية/قاعدة عمل أضف حالات إيجابية وحدّية وسلبية.
- **Implement:** اتبع نمط المشروع القائم؛ اختر أصغر diff، استعمل مكتبة موجودة موثوقة، لا تضف تبعية قبل تقييم المخاطر والتكلفة والصيانة. احتفظ بالتوافق الخلفي للعقود.
- **Verify:** شغّل الاختبار الأدنى المرتبط بالتغيير، ثم lint/typecheck/integration وبقية الاختبارات الملائمة. اقرأ مخرجات التشغيل، لا تساوِ نجاح التنفيذ بصحة الناتج.
- **Review:** افحص diff ونطاق التعديل والتسرب/الصلاحيات والاستعلامات والسرية وإمكان التراجع. المراجعة المستقلة أو الوكيل الثاني مفيدة للتغيير عالي المخاطر، ولا تحل محل الاختبار.
- **Handoff:** حدّث `CHANGELOG.md` والقرار/الوثيقة المتأثرة مع قبل/بعد، السبب، الملفات، اختبارات منفذة بنتائجها، اختبارات لم تُنفّذ، المخاطر، وروابط المهمة/commit إن توفرت. لا تنسب نشرًا لم يحدث.

## 3. بوابات الجودة بحسب الخطر
| درجة الخطر | أمثلة | أدلة قبول مطلوبة |
|---|---|---|
| منخفض | وثائق/صياغة أو تعديل UI معزول | diff محدود + فحص الروابط/البناء إذا تأثر |
| متوسط | مسار API أو حساب أو إصلاح وظيفة | اختبار مستهدف + حالات حدود + فحص رجعي للتبعيات |
| عالٍ | RLS/الصلاحيات، ترحيل DB، ماليات، بيانات طلاب، هوية | اختبارات وصول سلبي/إيجابي، عزل مستأجرين، خطة rollback/backup، مراجعة مستقلة، بيئة تجريبية قبل الإنتاج |
| حرج | بيانات حساسة أو إتلاف/استيراد واسع أو نشر إنتاجي مؤثر | ما سبق + موافقة المالك/الجهة المخوّلة وخطة استرجاع موثقة وفحص مراقبة بعد النشر |

- بوابات الأمن مستندة إلى **NIST SSDF 1.1** و**OWASP ASVS 5.0**: المصادقة، التفويض لكل عملية وسجل، عزل المستأجرين، التحقق من الإدخال، الجلسات، التخزين والأسرار، التدقيق. ليست شهادة امتثال.
- بوابة التوريد البرمجي: تثبيت إصدارات التبعيات، مراجعة المصدر والترخيص، فحص الأسرار والتنبيهات الأمنية حين تكون الأدوات متاحة؛ لا تثبّت خدمات مدفوعة أو ترفع بيانات خاصة لتفعيل فاحص.
- قاعدة البيانات: ترحيلات متدرجة وقابلة للتراجع حيث يمكن؛ تحقق من النسخ الاحتياطي والـRLS والـgrants والـconstraints وإعادة التشغيل بأمان قبل الترقية.
- الاختبارات: طبقات unit/integration/contract/E2E حسب أثر التغيير، بيانات صناعية، وحالات فشل واقعية؛ لا تفرض تغطية رقمية شكلية أو E2E ثقيلًا لكل فاصلة.
- الواجهات: اختبر RTL/العربية، الوصولية، الشاشات الصغيرة، حالات التحميل/الخطأ، وقارن اللقطات عند تغيير مرئي.
- الأداء: احصل على baseline بقياسات وبيانات ممثلة قبل التحسين، ثم قارن زمن/تكلفة/صحة النتائج؛ لا تدعِ تسارعًا بلا قياس.

## 4. الوكلاء والذكاء الاصطناعي
- `AGENTS.md` للتعليمات الموجزة الدائمة؛ `CLAUDE.md` يحيل إليها؛ هذه الوثيقة تُقرأ بحسب المهمة فقط لتقليل استهلاك السياق.
- يمنع العمل المتزامن على الملفات نفسها بلا فروع/worktrees مستقلة؛ يسبق الدمج فحص diff، تعارضات، ونتائج الاختبارات.
- إذا فشلت محاولتا إصلاح متتاليتان: توقّف عن ترقيع عشوائي، ثبّت الفرضيات والسجلات، أجرِ تحليل سبب جذري، وغيّر الخطة أو اطلب مراجعة ثانية.
- للأجوبة المولّدة من بيانات: أنشئ عينة مرجعية بأسئلة ومخرجات متوقعة، قيّم الصحة والمصدر ورفض الادعاء عند نقص الصلاحية، وافصل جودة النص عن صحة البيانات.
- لا تُنشئ قواعد تعلم من كل تفاعل؛ أضف فقط قواعد ملموسة متكررة مع تاريخ وسبب، وراجعها دوريًا لحذف المهجور.

## 5. التشغيل والقياس
- قبل النشر: تحقق من نقطة استعادة، وخطة إيقاف/تراجع، ومؤشرات صحة فعلية للمسار الحرج؛ لا تعتبر نجاح النشر وحده نجاح المنتج.
- راقب أخطاء الوظائف وصحة المخرجات ووقت الاستجابة والحوادث، دون تخزين أسرار/بيانات شخصية في السجلات.
- قِس ما ينفع القرار: lead time، معدل فشل التغيير، وقت التعافي، وإعادة العمل (مقاييس DORA)، إضافة إلى معيار نجاح المشروع؛ لا تصطنع baseline.
- خفف العبء: أولوية لإزالة الخطوات اليدوية المتكررة، وإغلاق المهام المكتملة، وتحسين الأخطاء المؤثرة قبل التوسع غير المطلوب.

### درب | PATH — ضوابط الموقع التعريفي
- `index.html` الحالي يحمل هوية درب | PATH؛ حافظ على الشعار والألوان والنصوص واللغات كما اعتمدها المالك ولا تبتكر تموضعًا تسويقيًا جديدًا.
- اختبر العربية RTL والإنجليزية LTR إن وُجدت، وتجربة الجوال والروابط ونماذج التواصل والظهور الصحيح في المتصفح قبل إعلان الجاهزية.
- انتبه للأمان والخصوصية عند نماذج جمع بيانات الأفراد؛ لا تنقل بيانات الزوار لخدمات طرف ثالث دون إذن.
- لا تنشر تغييرات أو تربط نطاقات/خدمات مدفوعة لمجرد تعديل التوثيق.
